# 00 Product Principles And Scope

## 文件角色

本文件是產品層最高 SSOT，定義：

- 產品本質
- 不可偏離的邊界
- 目前啟用版本的範圍
- 未來擴充時的判斷原則

如果其他文件與本文件衝突，以本文件為準。

## 產品名稱

今天吃什麼：命運遠征

## 一句話定位

一個奇幻冒險風的極輕量決策產品，幫大家在 1 到 2 分鐘內快速決定今天要吃哪裡。

## 產品母體與目前切片

- 產品母體：可模組化、可主題化的極輕量決策產品
- 目前啟用切片：以「吃什麼」為題目的單螢幕、無登入、同螢幕快速決策體驗
- 目前主題：奇幻冒險 / 命運遠征
- 目前目標：先把午餐、晚餐、飲料、甜點決策做得快、好懂、好玩

## 核心價值

本產品的核心價值只有兩個：

1. 低成本決策
2. 社交互動

補充原則：

- 解決的是猶豫成本，不是資訊稀缺
- 目標是快速推進到可接受的決定，不是找出理論上最完美的選項
- 社交互動是增益，不可壓過決策本身

## 核心使用者心智

本產品服務的是：

- 懶得選太久的人
- 選擇太多反而不想想的人
- 願意接受一點隨機感的人
- 希望決策過程有一點趣味的人
- 願意把日常小選擇交給輕鬆互動機制的人

## 第一性原則

### 1. 極輕量原則

- 產品必須容易理解
- 產品必須容易開始
- 產品必須容易結束
- 不得出現高操作成本
- 不得讓使用者有「我要先研究一下怎麼用」的感受

### 2. 快速出結果原則

- 核心流程必須短
- 單次使用應在 1 到 2 分鐘內完成
- 任何會明顯拖慢主流程的設計都應被高度質疑

### 3. 遊戲化包裝原則

- 遊戲化是包裝，不是主體
- 主題、視覺、文案、演出可以豐富，但不能增加理解負擔
- 產品應更像桌遊 / 派對工具，不像重度 RPG 官網或功能平台

### 4. 決策優先原則

- 決策是主體
- 社交是增益
- 分享、梗感、演出、合作都不能壓過「幫人做出決定」

### 5. 輕反悔原則

- 使用者可以輕度反悔
- 反悔機制必須簡單、快速、低摩擦
- 不可演變成多輪篩選、複雜比較或重度操控

### 6. 公平感原則

- 使用者必須相信結果可信
- 商業合作不得破壞公平感
- 任何贊助、加權、推薦位都必須可被誠實標示

## 不可破壞規則

未來任何版本都不得破壞：

1. 不能把核心流程做成多步驟繁瑣操作
2. 不能讓主題包改變產品本質
3. 不能讓內容擴充變成平台化失控
4. 不能讓商業合作干擾核心決策信任
5. 不能讓產品變成要登入才有價值
6. 不能讓產品變成資料很多但不想打開
7. 不能把產品做成「功能完整但不好用」的工具

## 目前啟用版本範圍

### 目前使用情境

- 同事站在一起快速決定午餐
- 朋友聚在一起決定晚餐、飲料或甜點
- 大家希望少討論、少猶豫，但過程有點好玩

### 第一版範圍

- 目前遠征地對應的 3 小時天氣預報驅動場景
- 單頁告示牌首頁
- 類型選擇
- 開啟今日遠征
- 隨機命運卡
- 命運揭示與翻牌演出
- 揭曉今日遠征目的地
- 結果階段的距離提示
- 地圖跳轉
- 一次保底重抽
- 特殊命運卡額外加送一次重抽

### 已啟用的產品化基線

- 餐廳主資料來源為公開 Google Sheet 即時資料
- repo 內保留本地快照作為 fallback snapshot
- 日常資料更新應以試算表為主，不要求每次重新部署網站
- 資料來源切換不能破壞既有抽選、重抽、場景與地圖跳轉

### 已啟用的 location-aware Phase 1 方向

目前正式產品化方向，不是把產品做重，而是把原本固定區域版本升級成「location-aware、但仍然低摩擦」的產品。

這個方向的核心原則是：

- 不加 login friction
- 不把定位做成每次進站都要填的 setup gate
- 不隱藏目前使用中的地區
- 永遠保留輕量人工修正路徑

長期正式策略固定為：

`detect-first, confirm-lightly, remember-locally`

也就是：

1. 優先幫使用者推測位置
2. 推測夠可信就直接套用
3. 以可編輯狀態顯示目前地區，而不是先擋住主流程
4. 本地記住上次接受的位置，避免重新整理後反覆詢問
5. 自動推測不足時，再請使用者輕量修正

目前已啟用的 Phase 1 執行方式：

1. 若有本地記住的位置，first paint 直接使用
2. 若還沒有本地位置，先沿用現有產品錨點 `臺北市中山區`
3. 使用者可隨時以輕量介面更改城市 / 地區
4. 餐廳候選池依 `district -> city -> fallback` 決定
5. 若目前遠征地有正式背景圖，背景優先使用該行政區圖資
6. 若目前遠征地尚無正式背景圖，回退到共享背景
7. 若目前遠征地有 CWA 鄉鎮 mapping，首頁天氣跟著該行政區走
8. geolocation / IP fallback 留到下一階段

補充說明：

- 上述 `geolocation / IP fallback` 指的是首頁 detect-first 流程
- 結果階段允許玩家主動觸發 browser geolocation，用來顯示遠征地距離
- 這個距離提示不能變成首頁 first paint 的阻塞式設定
- 一旦玩家在距離提示中成功授權，網站應本地記住最近一次可用座標，避免 refresh 後再次要求
- 首頁主位置語意應以 `預計冒險地` 呈現，而不是同時重複顯示多個看似相同但含義不同的位置欄位

### 第一版非目標

- 帳號系統
- 即時多人房間
- 排行榜
- 成就徽章
- 角色養成
- 複雜投票或對戰規則
- 深度搜尋與比較
- 平台式店家資訊頁
- 每次進站都要重新手動選城市 / 地區

## 可接受的延伸方向

- 午餐吃什麼
- 晚餐吃什麼
- 飲料喝什麼
- 下午茶吃什麼
- 聚餐去哪裡
- 約會去哪裡
- 商圈探索
- 旅遊中的小選擇
- 活動中的選擇題互動
- 依城市 / 行政區自動調整候選池的地點感知版本

## 不可偏離的方向

如果某個擴充需要以下任一項，就應被視為偏離產品骨架：

- 長時間搜尋
- 大量篩選
- 深度比較
- 註冊會員
- 複雜後台
- 大量社群互動
- 重複阻塞式地理位置設定流程

## 商業化原則

- 商業化只能是附加層，不能成為主設計核心
- 先有固定使用情境，再談商業掛載
- 商業合作必須明示、可標記、可追蹤
- 不可黑箱操控核心結果
- 不可讓合作內容壟斷使用體驗

## 成功定義

本產品的成功不是功能越多越好，而是：

- 使用者願意反覆打開
- 能進入固定日常情境
- 能縮短猶豫時間
- 能讓決策過程更輕鬆、有趣、自然
- 在不破壞極簡體驗的前提下，仍可承載更多主題、場景與內容

## 新增需求前的判斷問題

每次新增功能、主題、合作或場景前，都必須先回答：

1. 這個東西有沒有強化低成本決策？
2. 這個東西有沒有自然增強社交互動？
3. 這個東西會不會讓核心流程變慢、變重、變難懂？
4. 這個東西會不會讓產品更像平台而不是入口？
5. 這個東西是保護核心，還是在提前滿足想像？

若第 3、4、5 題偏負面，不應進核心產品。
